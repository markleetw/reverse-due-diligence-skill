# 報告章節骨架

預設章節如下。依調查結果增刪——**若某個面向查出了異常豐富或異常危險的東西，就給它一個獨立章節**，不要硬塞進既有結構。

| # | 章節 | 要點 |
|---|---|---|
| 01 | 一分鐘結論 | 六個 stat tile + 一段定調 + 一則好消息旗標 + 一則壞消息旗標。**先講結論** |
| 02 | 公司是什麼、怎麼賺錢 | 業務線總表（占比／成長率／本質），指向下一節 |
| 03 | 營收引擎拆解 | 每條線的「誰付錢、付多少、換到什麼」。含定價圖 |
| 04 | （選）高風險業務深挖 | 只在有結構套利、監管缺口或資產負債表風險時才開 |
| 05 | 上市與股價表現 | 價格節點圖 + 事件表。**明講從哪天算報酬差多少** |
| 06 | 財務軌跡 | 營收與 EPS 圖 + 年度表 + **對外敘事的用詞演變** |
| 07 | 營收結構與海內外占比 | 堆疊圖（不同期間對比）+ 市場飽和度判斷 |
| 08 | 低潮期 | 逐次拆四層，收在「會不會再發生」 |
| 09 | 創辦人與經營團隊 | 角色、背景、**公開能見度（高調／低調）**、經營風格線索 |
| 10 | 股東結構 | 表 + 近期股權變動 + 治理風險 |
| 11 | 人數、組織與薪酬 | 規模、組織圖、面試流程、薪酬三來源交叉比對、福利 |
| 12 | 組織風氣與風評 | 評分圖 + 一致的正面 + 一致的負面 + 外部聲譽風險 |
| 13 | 產品主導還是業務主導 | 雙欄對照證據 + 精確結論 |
| 14 | 前景推演與風險 | 基本盤推演（含關鍵假設）+ 風險清單依嚴重度排序 + 值得肯定之處 |
| 15 | 這份工作值不值得接 | 分項評分條 + 接的理由 + 不接的理由 + 建議做法 |
| 16 | 面試提問清單 | **依 P0／P1／P2 分級並標註「問誰」**，見下方 |
| 17 | 資料來源與方法說明 | 分組列出 + 方法與限制聲明 |

## 各節撰寫要點

**01 一分鐘結論**：使用者可能只讀這一節。要能獨立成立。壞消息旗標要具體到數字。

**05 股價**：不同起算點的報酬率差異，直接關係到股權談判。若曾大幅下跌又回升，明講「早期員工的股票大概率還在水下」。

**06 敘事演變**：列出各年度的關鍵詞。這是判斷「現在的董事會用什麼指標看產品」最快的方法。

**09 創辦人**：用 pill 標註能見度（非常高調／中高／低調）。高調且產品出身的 CEO，直接影響產品主管的 ownership 邊界——要在這節就點出來。

**12 風評**：把「一致出現在多來源的訊號」與「單一來源的個案」分開。負面訊號若彼此呼應（升遷低分 + 短年資 + 「人治」評論），要指出它們是同一件事的不同說法。

**14 風險**：依嚴重度排序，用旗標顏色分級。每條要寫「這個風險如果實現，對使用者的具體影響是什麼」。

**15 值不值得接**：這節必須有立場。評分條要註明是主觀評估，並為每個分數標示 **High / Medium / Low confidence**。分數回答「看起來有多好」，confidence 回答「有多確定」；詳細校準錨點見 `references/analysis-playbook.md` 第 20 節。收在「不要在拿到 offer 前決定，先用下一節的問題測試三件事」。

## HTML 實作

用 `templates/report-shell.html` 當起點。它已包含：

- 深淺色雙模式（OS 偏好 + 手動切換，兩者都要能覆蓋）
- 目錄、卡片、旗標（紅／黃／綠／中性）、pill 標籤、stat tile、評分條、可摺疊 details、面試題卡片
- 圖表繪製函式：**直條圖**（含虛線推估柱）、**正負值直條圖**、**節點折線圖**、**分組直條圖**、**百分比堆疊橫條圖**、**小倍數圖**、**橫條評分圖**、**區間橫條圖**
- 統一的 tooltip 綁定與深淺色重繪

`templates/report-shell.html` 是 renderer SSOT。**必須從完整 shell 開始，不得複製成 HTML fragment：輸出要保留 `<!DOCTYPE html>`、`<html>`、`<head>`、`<body>` 與完整 closing tags，且 `</html>` 必須是最後一個非空白內容。**產出報告時原樣保留整個 `<style>`，以及 `RDD_REPORT_DATA_START` 之前、`RDD_REPORT_DATA_END` 之後的共用 renderer JavaScript。正文內容可自由替換；圖表資料與呼叫只放在兩個 marker 之間。**不要為單次公司報告自行調色、改 spacing、另寫 chart library 或改 theme logic。**若既有元件不足，優先用既有 primitives 組合，而不是 fork renderer。

若執行環境提供資料視覺化指南或相關 Skill，動手前先讀；否則遵循本節既有的圖表規則。

**必做的品管**：

- 若能執行 packaged script，定稿前執行 `scripts/audit.py REPORT.html AUDIT_SPEC.json --renderer-template templates/report-shell.html`；document envelope 或 renderer parity 任一失敗都先修正，不交付。
- 若有 JavaScript runtime，可先抽出 inline script 做語法檢查。
- 若有 browser automation／headless browser，實際載入 HTML，至少檢查：console/page errors、深淺色切換、desktop/mobile overflow、圖表與目錄連結。
- browser QA 後要**實際看過畫面**——驗證器抓不到排版碰撞、標籤重疊與視覺層級問題。
- 若執行環境沒有 browser automation，至少做靜態檢查，並在交付時明確註明未執行 browser visual QA。

常見問題：軸單位標籤與第一個資料標籤重疊、堆疊圖窄色塊上的白字對比不足（淺色系色塊要改深色字）、時間軸上相鄰標籤重複。

## 交付

1. 以執行環境可用的檔案交付方式提供自包含 HTML。
2. 若環境無法輸出檔案，改以完整 Markdown 報告交付，保留相同的分析結構、來源與面試題。
3. 若環境支援持久化 artifact／library，且使用者可能反覆回來查看，可另外保存；後續更新應同步更新該份持久化版本。
4. **提醒保密**：這類報告含有對雇主的尖銳評論，不適合公開發布。若使用者想公開，建議另做一份匿名化、去掉個人求職判斷的產業分析版


## 面試題清單的分級（不做這件事，清單就等於沒用）

一份完整調查很容易累積出 25–30 題，**而一場面試問得完的大約是 5–8 題**。不分級的清單，使用者在現場只會從第一題開始問，然後在最重要的題目之前就沒時間了。

### 三級 + 一個外掛

| 級別 | 定義 | 數量 |
|---|---|---|
| **P0** | 不問到答案就不該接。決策性。 | 4–6 題 |
| **P1** | 影響談判籌碼與期待設定。 | 6–8 題 |
| **P2** | 加分題，展現做過功課。有時間再問或留到第二輪。 | 其餘 |
| **自行查證** | 公開資料查得到的，不要浪費面試時間問 | 視情況 |

最後一類最常被忽略，但它同時傳達一個訊息：**查得到還在現場問，反而顯示功課沒做完。**

### 一併標註「問誰」

CEO／用人主管、HR、財務或 IR、以及「跨部門面談對象」問到的東西完全不同。薪酬結構問 HR，產品決策權問 CEO，債權明細問財務——**標錯對象，好問題也會浪費掉**。

### 交付一份「現場速查」

在分級清單之前，放一個**只有 P0、每題壓縮成一行**的方框。使用者真正會帶進面試的是這個，不是完整清單。

### 合併重複題

長報告經多輪增補後，同一個問題常以不同措辭出現三四次（例如「2024 診斷」「台灣定位」各出現兩次）。**定稿前務必逐題比對合併**——重複題會稀釋清單的可信度，也讓使用者誤以為題目比實際更多。
